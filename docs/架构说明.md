# 架构说明

这个仓库本质上是套在 ComfyUI 外面的一个「控制器」。所有 MiniMax H3 的扩散、音频解码、
视频编码仍然由 ComfyUI 完成，控制器只负责编排。

## 每一段视频，控制器做什么

1. 从 `config.json` 里读这一段的提示词、时长和是否二采；
2. 现搭一张 ComfyUI API 图（不是读 `api_workflows/*.json`，那些只是原始导出的对照文件）；
3. 在开始出任何一段完整视频**之前**，先把整条关键帧链串完；
4. 每一段生成的尾帧，就是下一段的首帧（同一张图，不重新摇）；
5. 支持分镜硬切：`continue_from_previous = false` 时，为下一段单独生成首帧，
   并在两段之间插一段转场视频；
6. 提交到 `/prompt`、等 `/history`、把结果记进 `.state.json`；
7. 用 FFmpeg 统一分辨率、拼接分段视频和转场。

开场关键帧刻意不从 `reference_images` 里拿固定首帧：先跑一条 5 秒 H3 草稿，
取它的第一帧当开场帧；之后每一段的尾帧都从「上一段尾帧 + 下一段提示词」长出来。
**所有关键帧就位后才开始跑完整视频**，这样中间停下来换图、改词都不用重跑整条链。

## 二采（two_pass）走的路

和原始 ComfyUI 工作流一致：

```
AV 潜空间 -> 拆视频/音频 -> 视频潜空间 2x 放大 -> 合回 -> MMH3 Ultimate Upscale
```

第三方放大器有时会在开头吐出两帧条纹。控制器在把这一段写进链之前，会用该段的
首帧锚点把这两帧覆盖掉（`repair_two_pass_opening`）。

## 为什么编排放在 Python 里

ComfyUI 的 UI 本身没法在一张可复用图里同时管住「任意段提示词 / 每段时长 / 每段二采开关 /
上游结果哈希」。这些编排性质的东西留在 Python 里，收益是**每一段仍然是一次普通的
ComfyUI 执行**——能在 ComfyUI 自己的历史里查、能单独重跑、能单独看日志。

节点（Director）只是给这套 Python 编排套了个可交互的壳：

```
ComfyUI 工作流（Director 节点）
      │  点 Queue
      ▼
director.py（注册节点 + HTTP 路由 + 起 worker 线程）
      │  subprocess
      ▼
run_h3_long_video.py（真正的编排：关键帧链 → 分段视频 → 合并）
      │  HTTP /prompt
      ▼
ComfyUI 本体（真正干活）
```

具体谁调谁、工作流之间怎么衔接，见 `工作流关系.md`；每个文件放在哪，见 `文件位置说明.md`。
