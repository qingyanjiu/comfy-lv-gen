# 配置参考

故事板中每个字段的完整说明见：

`docs/分镜JSON.md`

本文档解释仓库中所有用户可配置项。配置文件分为四层：

1. ComfyUI Director 节点控件
2. Director 节点故事板 JSON
3. 仓库根目录 `config.json`
4. `advanced_overrides` 本次任务覆盖 JSON

## Director 节点控件

| 控件 | 作用 | 默认值 | 何时覆盖其他配置 |
|---|---|---:|---|
| `storyboard` | 填写每段提示词、秒数和局部二采设置 | 当前示例故事板 | 控制每段内容 |
| `reference_notes` | 说明每张参考图负责身份、脸型、发型、服装等哪些特征 | 图1/图2说明模板 | 自动加到每一段提示词最前面 |
| `steps` | 一采步数 | `4` | 覆盖全局和高级覆盖里的 `steps` |
| `two_pass_steps` | 二采步数 | `2` | 覆盖全局和高级覆盖里的 `two_pass_steps`。**Director 节点上的控件优先**，Queue 之前先对一眼。默认 4+2 是 2026-11-05 定的（一采 4 步、二采 2 步，二采默认开） |
| `seed` | 固定随机种子 | `0` | `randomize_seed=false` 时使用 |
| `randomize_seed` | 每次任务自动生成新种子 | `true` | 为 `true` 时忽略固定 `seed` |
| `first_frame` | 可选的首段固定首帧 | 未连接 | 连接后跳过一次第一段开始关键帧生成 |
| `sampler` | 一采和二采共用的采样器 | `res_multistep` | 覆盖 `sampler` |
| `scheduler` | 一采和二采共用的调度器 | `simple` | 同时覆盖 `scheduler` 和 `two_pass_scheduler` |
| `megapixels` | 一采基础生成像素量 | `0.3` | 覆盖 `megapixels` |
| `final_width` | 最终视频宽度（选「自定义」时才生效） | `832` | 覆盖 `final_width` |
| `final_height` | 最终视频高度（选「自定义」时才生效） | `1472` | 覆盖 `final_height` |
| `two_pass_mode` | 全局二采模式 | `跟随每段 JSON` | 可强制所有段一采或二采 |
| `force` | CLI 缓存强制重跑开关 | `false` | Director 每个任务目录都是新的，通常无效 |
| `reference_1` | 必选参考图 | 无 | 必须连接 IMAGE |
| `reference_2` 到 `reference_9` | 可选参考图 | 未连接 | 每张都是 IMAGE，最多共 9 张 |
| `advanced_overrides` | 本次任务的高级 JSON 覆盖 | `{}` | 节点专用采样控件随后覆盖同名值 |
| `job_name` | 任务名，拼成 `日期-名称` 当任务号和文件夹名 | 空（用时间戳） | 只影响命名，不影响生成 |
| `keyframe_backend` | **全局配置**：关键帧由谁来画。`H3 自己出` / `Qwen-Image-Edit 2511` / `Qwen-Image-2.1` / `只用手动图` | `H3 自己出` | 选 Qwen 时 runner 用该模型**自动出整条任务的首尾帧**；只有 `manual` 才跳过生成、等你放图 |
| `resolution` | **成片分辨率预设**，默认档位：`832x1472` / `720x1280` / `1080x1920` / `480x854` / `自定义` | `832x1472（9:16 默认）` | 选中预设就盖掉 `final_width` / `final_height`；选「自定义」才用那两个 INT 控件 |
| `video_backend` | **出视频跑在哪**：`本地 ComfyUI` / `RunningHub 云端` | `本地 ComfyUI` | 只影响视频阶段。云端配置见 `config.json` 的 `runninghub` 块，见下文「云端出视频」 |

`resolution` 是 2026-11-02 新加的，`video_backend` 是 2026-11-04 新加的，两个都**排在控件列表末尾**——老工作流的 `widgets_values`
是按顺序存的，插在中间会把后面的值顶到新控件上。`resolution` 同时决定两件事：

1. 成片尺寸；
2. **关键帧的目标尺寸**：runner 出完图会立刻把首尾帧对齐到这个分辨率
   （见 `docs/关键帧生成.md` 的「关键帧对齐成片分辨率」），所以关键帧和成片永远同尺寸同比例，
   剪辑阶段不再需要拉伸。

> **2026-11-04：`keyframe_steps` 已删除。** 关键帧和正片现在共用 `steps`
> （H3 关键帧只是抽一张静态图，没有必要单独一个步数旋钮；两个旋钮并存时
> 改了 `steps` 忘改它，就会出现「关键帧糊、正片清」）。旧工作流打开时前端会
> 自动把错位的 `widgets_values` 摆正（`web/director.js` 的
> `migrateLegacyKeyframeSteps`），后端也会把落到 `advanced_overrides` 上的
> 纯数字当 `{}` 处理。

### 分辨率档位是配置项

下拉里的档位不写死在代码里，改 `config.json` 就能增删（改完重启 ComfyUI 生效）：

```json
"resolution_presets": {
  "832x1472（9:16 默认）": [832, 1472],
  "720x1280（9:16 标清）": [720, 1280],
  "1080x1920（9:16 高清）": [1080, 1920],
  "480x854（9:16 省显存）": [480, 854]
},
"resolution_default": "832x1472（9:16 默认）"
```

- 值的写法：`[宽, 高]`、`{"width":…, "height":…}`、或 `"832x1472"` 字符串都行；
- **标签格式必须是「宽x高（说明）」**——面板摘要靠这个正则把标签解析回尺寸，
  不按格式写会显示成 `?×?`（生成仍然按 JSON 里的数值走）；
- 非法条目（0×0、不是数字）会被整条丢掉，回落内置的四档，不会拿坏尺寸去跑；
- `resolution_default` 写不在表里的值，自动落到第一档；
- 想加一档比如 `864x1536`：加一行 `"864x1536（1.33MP）": [864, 1536]` 即可，前端不用改。

**为什么默认 832×1472**：它是 H3 一采 `416×736` 的整数 2 倍（`megapixels=0.3` + `two_pass_scale=2`），
成片阶段零缩放。720×1280 要缩到 0.87×，1080×1920 要放大 1.30×，都多一次重采样。

### 关键帧对齐成片分辨率（config.json 侧）

| 字段 | 作用 | 默认 |
|---|---|---:|
| `keyframe_align` | `outpaint`：铺灰底走扩图 LoRA 补真实场景（4:5 参考图必须用这档）；`crop`：等比放大后中心裁切（省时间，但会裁掉桌面）；`off`：保持旧行为（关键帧维持生成尺寸） | `outpaint` |
| `keyframe_reference_preexpand` | `true`：关键帧开跑前把参考图**预扩一次**到成片比例（存任务目录 `reference_expanded.png`），之后所有关键帧共用这张扩好的图。背景延伸每段一致（以前每段各扩一次，补出来的桌面/背景细节都对不上），且首帧出图直接命中目标尺寸，整条链路零逐帧扩图（每段省约 35s）。断点续跑时直接复用，不会重扩；扩图失败自动退回逐帧扩图的旧行为。只扩 `reference_images[0]`（图1/画布角色），其余身份参考不扩 | `true` |
| `keyframe_locks` | 关键帧提示词是否追加三条全局锁（头发 / 视角 / 光线色调） | `true` |
| `keyframe_locks_prompt` | 三条锁的具体措辞，留空用内置版本 | 见 config.json |
| `keyframe_qwen_megapixels` | 2.1 出图的像素预算：按图1比例 × 这个值、32 对齐 | `1.05` |
| `keyframe_outpaint_megapixels` | 扩图画布的像素预算，32 对齐后自动挑比例最准的一组；实际会取 `max(它, 目标像素)`，避免扩完再放大 | `0.75` |
| `keyframe_outpaint_steps` | 扩图采样步数 | `20` |
| `keyframe_outpaint_unet` | 扩图用的底模（官方 int8，别换成 ray 微调版） | `qwen_image_2.1_int8_convrot.safetensors` |
| `keyframe_outpaint_lora` | 扩图 LoRA | `Qwen-功能2.1\Qwen21-图像扩展qwen-image-2.1-outpaint-v2.safetensors` |
| `keyframe_outpaint_prompt` | 扩图触发词，只描述"把灰区补成场景"，不描述内容 | 见 config.json |

`outpaint` 只在「关键帧比例与目标差 > 0.5%」时才真的跑（每帧多约 35 秒）；比例本来就对得上时
只做 resize。扩图失败会自动退回 `crop`，不会让整条任务挂掉。

**手动换帧不用管尺寸**：面板「替换」上传的图和磁盘上被覆盖的 `segNN_*_manual.png`，
都会在入口处按任务分辨率做一次等比 cover 裁切，所以你丢 4:5 截图进去也能直接用。

## 故事板 JSON

`storyboard` 接受以下形式：

```json
{
  "segments": [
    {
      "seconds": 5.0,
      "two_pass": false,
      "prompt": "这一段的动作和运动提示词",
      "end_frame_prompt": "这一段结束时静态画面的描述",
      "start_frame_prompt": "新分镜开始时的静态画面",
      "hold_composition": false,
      "free_end": false,
      "continue_from_previous": true,
      "transition_seconds": 1.0,
      "transition_prompt": "从上一镜头自然过渡到新镜头"
    }
  ]
}
```

也可以直接传数组，但推荐保留 `segments` 外层对象。

| 字段 | 类型 | 必填 | 作用 |
|---|---|---:|---|
| `seconds` | 数字，必须大于 0 | 是 | 该段视频时长。实际输出帧数按 24 fps 计算并截断 |
| `two_pass` | 布尔值 | 否，默认 `false` | `false` 一采，`true` 二采；最终还受全局 `two_pass_mode` 控制 |
| `prompt` | 字符串 | 是，不能为空 | 该段独立的动作、场景、镜头和声音描述 |
| `end_frame_prompt` | 字符串 | 否 | 用于生成该段结束关键帧；省略时使用 `prompt` |
| `start_frame_prompt` | 字符串 | 否 | 分镜断开时用于生成独立开始关键帧；省略时使用 `prompt` |
| `hold_composition` | 布尔值 | 否 | `true` 不生成新结束帧，直接使用开始帧；`false` 生成独立结束关键帧 |
| `free_end` | 布尔值 | 否，默认 `false` | `true` **完全不锚尾帧**：本段自由收尾，下一段的首帧取本段渲染出来的最后一帧（见下节） |
| `continue_from_previous` | 布尔值 | 否 | 覆盖全局 `chain_segments`；`false` 表示启用分镜断开 |
| `transition_seconds` | 数字 | 否 | 分镜淡入淡出或生成式转场的时长 |
| `transition_prompt` | 字符串 | 否 | `generated` 模式下生成式转场的提示词 |

### 一致性字段（`pipeline.py --storyboard` 分镜，2026-11-09 新增）

下面这些是**流水线分镜**字段，不是 Director `config.json` 的字段，别混用。

| 字段 | 作用 |
|---|---|
| `bg_ref` | 无人场景空镜文件名（`Shared/input/` 下）。全片唯一资产，各镜派生，不逐镜重生成 |
| `space_lock` | 固定方位词，例「门在左、橱窗在右、主光左上，全片不镜像」；`check` 缺它会提醒 |
| `camera_move` | 段级机位变化（拉/推/摇）。有它时背景一致性只存档不刷提示 |
| `lighting_fx` | 段级 `true` 表示发光特效题材；画质闸门与背景闸门都只存档（沿用既有约定） |
| `source_frames` | **复刻链路**：`{"dir": "原片抽帧目录", "pattern": "shot_{i:03d}_{which}.jpg", "seed_base": 20261108, "out_dir": "项目/work/k2_refs", "out_name": "s{idx:02d}_{which}.png"}`。可选 `prompt` / `workflow` / `nodes`；不写就用 `scripts/source_frames.py` 里的唯一默认值 |
| `frame_exact` | **逐帧精确复刻**：`{"source_video": "原片.mp4", "start": 1.433, "end": 5.433, "output_path": ".../release/video.mp4", "identity": "一位 26 岁日本男性，深红长发，黑金长大衣", "seed": 20261109, "mode": "full", "temporal_smooth": 0.12, "max_frames": 130, "keep_audio": true}`。命令 `pipeline.py frame_exact --storyboard sb.json`；`check` 会走专用校验，不套 9:16 / 5s / 动作字段规则。`identity` **必须显式写死性别**；跨角色连续段用 `characters: [{start,end,identity}]` |

`source_frames` 子字段：`dir` 必填；`pattern` 默认 `shot_{i:03d}_{which}.jpg`
（可用 `{i}` `{idx}` `{which}`）；`seed_base` 不写则由分镜路径派生、自动避开坏种子
100000；`out_dir` / `out_name` 只产出**给人看的副本**，`state.first/last` 一律记
`Shared/input/` 下的规范名，保证 `push` / `video` 的 `basename()` 能直接用；
`nodes` 是换工作流时的节点映射，格式 `{"10": [0, "image"], "40": [0, "prompt"],
"32": [0, "prefix"], "30": [0, "seed"]}`。

复刻链路命令：

```bash
pipeline.py source_frames --storyboard sb.json                  # 全部段（自动断点）
pipeline.py source_frames --storyboard sb.json --segs 4,8       # 指定段，逗号分隔
pipeline.py source_frames --storyboard sb.json --force          # 忽略断点强制重绘
```

它把每段原片的 `first` / `last` 帧**各自独立重绘**（同模型 / 同提示词 / 同 seed），
结果写进 `state`，后续照常 `push → resume`。自带 4 次失败重试 + 服务自愈、
配置指纹断点（prompt / 工作流 / seed 一变自动重绘）、历史 `out_dir` 成对帧自动
adopt。**不要用 `frames` 跑复刻，也不要把首帧 A 当输入去推尾帧**——2.1 / 2511
都会把构图焊死在 A 上。

背景一致性结果写在 `state` 的 `bg_qa`：`bg_ssim` / `bg_changed` /
`bg_hist_corr` / `bg_layout_corr`，提示级、不阻断出片。两条链路都走
`consistency.report()` 这一个出口；可用
`python <skill>/scripts/consistency.py --first a.png --last b.png` 单独量
（`<skill>` = `D:/Comfy-Desktop/.workbuddy/skills/h3-long-video`）。

**唯一源码**：改代码只改 `<skill>/scripts/`；节点仓库
`h3-long-video-repo/skill/` 是同步副本，改完跑
`python <skill>/scripts/sync_repo.py --apply`，再 `--check` 应为 `ALL SYNCED`。

### 段长建议：≤4 秒（2026-11-02 实测）

同一个「抬手碰锁骨 → 放手微笑」场景、同一种子、同配方（Qwen-2.1 关键帧 + ray 20 步 + 四项锁）：

- **4 秒段**：全程稳定——衣服、头发、景别 8 个抽样帧零漂移，段间接缝自然。
- **6 秒段**：首尾帧都对（QA SSIM ≈ 0.98），但**中段**在 6.0–8.0s 处自己推成特写、头发散开，9.8s 才拉回半身。关键帧锁只约束首尾，管不了段内。

漂移是 H3 模型在长段里的自身行为，提示词写「镜头完全静止」也拦不住。所以长动作请拆成多个 ≤4 秒的段（每段一个明确的小动作），而不是拉长单段秒数。

### 静止压缩 static_compact（解决「中间卡了一下」）

H3 的段有个固定毛病：4 秒的段，动作 1.8 秒就演完，剩下 2 秒人物原地定格；而且动作本身是**断续**的——抬手 → 停 → 再继续。首尾帧都对、QA 也过，但拼起来就是「停一秒再接下一段」，很容易被误判成转场问题。实测（2026-11-02，抬手碰锁骨）：

- seg1 尾部定格 53 帧（2.21s）；成片里还夹着**开头 1.12s、中段 0.83s** 的静止。

只剪尾巴消不掉中段，所以默认开启**整段静止压缩**：检测每段所有「真静止」区间（头部/中段/尾部），把定格抽稀到保留帧数，**动作区一帧不动**，音轨按同一时间轴同步裁剪。静止帧之间几乎完全一样，抽稀看不出跳帧，只是节奏不拖了。

实测同素材：8.00s → 5.29s（默认 0.12s），所有静止区间压到 ≤0.2s，动作链完整。

**判定口径是 p99 而不是均值**：缓慢抬手的帧差均值（1.1）和真静止（0.8）同一量级，均值分不开；p99 抓「局部像素大幅移动」——手一动就 10~45，纯呼吸/噪声只有 2~8。阈值 9.0 就是这条分界线。

| 配置 | 默认 | 作用 |
|---|---:|---|
| `static_compact` | `true` | 拼接前压缩每段的定格；设 `false` 关闭 |
| `static_compact_threshold` | `9.0` | 判定「静止」的 p99 帧差阈值（0–255） |
| `static_compact_hold_seconds` | `0.12` | **每处定格剪完保留多久（秒）**，0.12×24fps≈3 帧；0 = 只留 1 帧（剪得最狠） |
| `static_compact_min_seconds` | `0.4` | 头/尾定格不足这个时长不动 |
| `static_compact_mid_min_seconds` | `0.4` | 中段定格不足这个时长不动 |
| `static_compact_min_saving` | `0.3` | 整段压不了 0.3s 就不折腾 |
| `static_compact_max_ratio` | `0.9` | 静止占比超过 90% 判为空镜/慢动作，整段跳过 |

`static_compact_hold_seconds` 同时在 Director 面板上暴露成「定格保留(秒)」控件（在控件列表最后），单个任务可以临时改；不填就用 `config.json` 的值。

老配置里的 `static_compact_head_keep` / `mid_keep` / `tail_keep`（帧数）仍然认：写了就以它为准，没写才用 `hold_seconds` 换算，方便个别段精调。

实测同一段素材（4s + 4s，抬手碰锁骨）：

| 保留秒数 | 保留帧 | 成片时长 |
|---:|---:|---:|
| 0（只留 1 帧） | 1 | 4.96s |
| 0.12（默认） | 3 | 5.29s |
| 0.30 | 7 | 6.08s |
| 不限（关掉） | 全部 | 8.00s |

保护：动作区一帧不动（只有静止区间被抽稀）；检测或编码失败时保留原段继续拼接；压缩不影响 ComfyUI 生成缓存。

### 别拿剪帧去补「两张图不一样」（2026-11-04 实测）

`static_compact` 只解决**段内真定格**（p99<9 的帧）。如果「中间卡一下」来自
**拼接点前后根本不是同一张关键帧**，剪静止帧治不好，越剪越糟：

- coffee 分镜（3 段 16.21s）实测相邻段尾/首关键帧灰度 MAE 8.25 / 9.46，
  约 19% 像素差 >10——2.1 后端的 `chain` 不复制首帧，两段各自独立生成；
- 用 p99 找出全片 86 帧 / 3.58s 定格，温和档（保留 0.12s）→ 13.99s、
  激进档（头尾定格全删）→ 12.83s，用户反馈**「去得太多了」**；
- 最终采用 **一帧不剪 + 两个接缝各 0.25s 短叠化** → 15.71s，动作链完整、无重影。

判据：先抽拼接点前后各 3~4 帧横排看，**看得见两张不同的脸/手位就是键帧不匹配**，
该修的是接缝不是帧数。姿势差很大时不要叠化（0.4s dissolve 会出双影，
见 skill `SKILL.md` 的「段间接缝」反例），老实用硬切。

skill 流水线（独立实现，不受本文件配置控制）用 `join_dissolve_seconds: 0.25`
或 `merge --join-dissolve 0.25` 实现这一版；本仓库的 `static_compact*` 调不到它。

画面有 N 个 `segments` 元素，就会自动循环生成 N 段，不要求固定段数。

## 自由尾帧 free_end（跨度为 10 秒以上时用它）

默认每段都会生成一张「尾帧」当锚点。但尾帧其实是一段
`keyframe_draft_seconds`（默认 5 秒）草稿的最后一帧——**5 秒演不完的动作，模型只能靠
改景别、改表情来假装到达终点**（实测：走 10 米 → 变半身/胸像；起身转身走远 → 变成凑近
镜头微笑）。这类段落应该关掉尾帧锚点：

```json
{ "seconds": 15, "prompt": "她一路走到长椅旁", "free_end": true }
```

`free_end=true` 时：

| 行为 | 说明 |
|---|---|
| 关键帧 | 只生成首帧，尾帧**不生成**，面板上显示「自由尾帧」占位 |
| 视频 | 该段 `last_frame=None`，模型自己决定停在哪一帧 |
| 下一段 | 链式段的首帧 = **本段渲染出来的最后一帧**（`state.segments[i].last_frame`），面板显示「接视频末帧」 |
| 若本段还没渲染 | 下一段首帧显示「待定首帧」，等视频阶段按顺序渲染时自动填入 |
| QA | `last_frame_ssim` 记为 `null`（没有锚点可比），其余指标照常 |

因此 `free_end` 会改变闸门节奏：**自由尾帧之后的段落，首帧要等上一段视频渲完才存在**。
关键帧确认页上出现「待定首帧」是正常的，不是缺帧，也不会阻塞 `--stage videos`
（`missing_keyframes` 会跳过 `free` / `pending-video` / `from-video` 三类帧）。

想反悔：在「自由尾帧」占位卡上点 **替换** 上传一张图，这一侧就变回固定锚点；
或者把 `free_end` 改回 `false` 重跑关键帧。

### 实测（15 秒「走向长椅」段落，同一首帧、同一种子）

| | 固定尾帧锚点 | `free_end` |
|---|---|---|
| 尾帧锚点 | AI 生成的胸像特写（长椅顶到镜头前） | 无 |
| 视频真实末帧 | 三分身、长椅在画面左侧 | **全身带鞋、长椅自然落在身侧** |
| 下一段起始帧 | 那张胸像锚点（和视频实际结尾对不上） | **视频真实末帧**（无缝） |
| 首帧相似度 | 0.938 | 0.931 |
| 静止比例 | 0.0 | 0.0 |

结论：跨度为 10 秒以上的位移段落，`free_end` 明显更自然，而且**消除了「锚点 vs 实际结尾」的错配**。

### 已知遗留：中段镜头呼吸
这条段落两个版本都会「0–3 秒全身 → 4–8 秒缓慢推近成半身 → 12–15 秒再拉回全身」。
`video_camera_continuity: true`（把跟拍指令同时写进**视频**提示词）实测**没有消除**这个呼吸，
所以默认关闭。真正稳的办法是缩短单段（≤6 秒）或改成横向走过画面。

`two_pass_mode` 的优先级高于每段 `two_pass`：

| 模式 | 结果 |
|---|---|
| `跟随每段 JSON` | 使用每段的 `two_pass` |
| `全部一采` | 所有段强制 `false` |
| `全部二采` | 所有段强制 `true` |

## 参考图说明 reference_notes

> `reference_notes` 会**前置**到每一条提示词（段/首帧/尾帧/转场），所以身份、服装、
> 全局禁止项都写在这里，段落里不要重复。提示词写法的完整规则见 `提示词指南.md`。

参考图会作为 IMAGE 传给 H3，但“图1代表什么、图2代表什么”需要写在 `reference_notes`。这段文字会自动加在每一段 `prompt` 前面，例如：

```text
Picture 1（参考图1）是<女主角>的主要身份、脸型、五官、发型和身高比例基准。
只有剧情已经换好最终服装后才参考它的服装；试穿和换装阶段严格跟随每段提示词。
Picture 2（参考图2）只用于稳定中性表情、眼型、鼻型、脸型和闭嘴嘴宽，不复制其白色上衣和背景。
Picture 3（参考图3）只用于参考裙摆和鞋子细节，不覆盖图1的人物身份，不复制图3的表情。

所有段落必须保持与上述图片一致的<女主角>，严格参考脸型、黑色长发和身体比例。
不得混入其他人物的脸、发型或年龄感；衣服随剧情变化，不能把同一套衣服强加到所有段落。
```

如果连接了 3 张以上图片，必须继续写清楚 `Picture 3`、`Picture 4` 各自负责什么。没有用途的图片不要连接，因为互相冲突的参考图会让 H3 混合不同人物的特征。

连接顺序会影响 `Picture N` 的编号：

```text
reference_1 → Picture 1 → ref_image_0
reference_2 → Picture 2 → ref_image_1
reference_3 → Picture 3 → ref_image_2
```

建议参考图组合：

1. 一张清晰的主要身份图，最好能看清脸、发型或服装。
2. 一张清晰的正脸中性表情图，用于稳定五官和闭嘴嘴宽。
3. 其他图片只承担单一用途，例如侧面、背面、鞋袜或特定服装细节。

不要同时连接多张来自不同人物、不同年龄段或明显不同服装的图片。

参考图约束是生成式引导，不是像素级换脸。如果人物仍然不像，应优先：

- 减少相互冲突的参考图
- 把最可靠的身份图放在 `reference_1`
- 在 `reference_notes` 中逐图说明用途
- 删除参考图里不需要被复制的背景和服装描述
- 将 `ref_image_size` 在 `advanced_overrides` 中改为 `max`

### 画幅和长度

| 配置项 | 默认值 | 作用 |
|---|---:|---|
| `aspect_ratio` | `9:16 (Portrait Widescreen)` | H3 的分辨率选择预设，必须保持竖屏 9:16 |
| `megapixels` | `0.3` | 一采基础像素量；会按 32 像素网格对齐 |
| `fps` | `24` | 当前代码只允许 24 fps |
| `final_width` | `704` | 最终成片宽度 |
| `final_height` | `1216` | 最终成片高度 |

当前 `9:16` 预设经过 32 像素对齐后，一采实际尺寸为 `416×736`（`megapixels=0.3`），二采和最终成片为 `704×1216`。

注意：`megapixels` 越低，32 像素取整带来的宽高比偏差越大（`0.3` → `416×736` 比值为 0.565，关键帧 `0.6` → `608×1056` 为 0.576），会让关键帧与视频帧构图轻微不一致，属于正常现象，QA 已按裁切对齐处理。

每段请求时长会换算为帧数，并向上对齐到 H3 要求的 `帧数 % 17 == 5`。输出仍会裁剪为该段配置的精确秒数，避免编码多出几十毫秒。

当请求帧数**正好**等于合法长度时（例如 8 秒 = 192 帧），H3 返回的最后一帧是坏的：
整帧竖向拖影、像几张画面叠在一起。平时这一帧落在裁剪范围之外，会被丢掉，看不出问题；
但正好对齐时就没有多余帧可裁，它会变成片子的最后一帧，而且**节点 38 保存的「上一段末帧」
也来自这一帧**，于是脏帧会被下一段当首帧继承。

`tail_guard_frames`（默认 `2`）就是为此加的保险：多要几帧，输出时再裁掉。
只有「正好对齐」的时长会因此多花一点算力（8 秒从 192 帧变 209 帧，约 +9%），
其它时长（5/6/9/12/15 秒等）帧数不变。设成 `0` 可关闭（不推荐）。

| 配置项 | 默认值 | 作用 |
|---|---:|---|
| `tail_guard_frames` | `2` | 额外多生成的帧数，用来丢弃末尾的坏帧 |

`hold_composition=true` 时：

```text
本段开始关键帧 → 本段 first_frame
本段开始关键帧 → 本段 last_frame
```

不生成新的结束关键帧，首尾被同一张图约束。适合站定、稳定构图镜头，不适合换衣服或明显改变位置。

`hold_composition=false` 时：

```text
本段开始关键帧 → 本段 first_frame
end_frame_prompt → 新结束关键帧 → 本段 last_frame
```

先生成独立的结束关键帧，再用两张不同的图约束完整视频，允许换装、上车、下车和场景状态持续推进。

### 分镜断开与转场

默认 `chain_segments=true`，上一段结束关键帧会直接作为下一段开始关键帧。

当某段需要新的镜头角度、地点或时间状态时，在该段填写：

```json
{
  "continue_from_previous": false,
  "transition_seconds": 1.0,
  "start_frame_prompt": "新镜头开始时的静态画面",
  "transition_prompt": "从上一镜头平滑转入新镜头"
}
```

此时流程会：

1. 不使用上一段尾帧作为新段首帧。
2. 根据 `start_frame_prompt` 和参考图生成独立开始关键帧。
3. 生成一段从上一段结束帧到新段开始帧的 H3 转场视频。
4. 输出顺序为“上一段视频 → 转场 → 新段视频”。

默认 `transition_mode=fade` 使用 FFmpeg 在分镜边界淡出到黑再淡入，不额外调用 H3，
也不会增加成片总时长。`transition_seconds` 是跨越边界的淡出和淡入总时长。

如果改为 `transition_mode=generated`，才会生成独立的 H3 转场视频，并增加最终时长。

第一段开始关键帧：

```text
第一段提示词 + 参考图
→ H3 短草案
→ 提取草案第一帧
```

不会把参考图文件直接作为第一段的固定首帧。

之后按段链式生成结束关键帧：

```text
开始关键帧 + 本段 end_frame_prompt
→ H3 短草案
→ 提取草案最后一帧作为结束关键帧
→ 下一段直接复用该结束关键帧作为开始帧
```

全部关键帧完成后才生成正式视频：

```text
开始关键帧 → H3 first_frame
结束关键帧 → H3 last_frame
→ 生成正式段视频
→ 按需执行二采
```

第一段如果没有单独填写不同的 `end_frame_prompt`，会直接使用开始关键帧草案
中已经生成的最后一帧作为第一段结束帧，不会为第一段再提交一次结束帧草案。
只有第一段填写了独立结束描述时，才会额外生成第二个关键帧草案。

关键帧默认使用 `keyframe_megapixels=0.6`、`steps`（与正片同一个步数）和
`keyframe_ref_image_size=max`，正式视频仍使用较轻量的 `megapixels=0.3`。
这样只在关键帧阶段增加计算，避免每一段视频一采都变慢。

参考图最多 9 张，全部传递到 H3 的 `ref_images.ref_image_0..8`。

`first_frame` 是独立于 9 张参考图的可选图片输入：

- 只用于第一段固定开始帧。
- 连接后不会额外生成第一段开始关键帧。
- 它不占用 `reference_1..9` 的编号。
- 如果希望“第一张图固定开头、其他图片作为身份参考”，把第一张图只接到
  `first_frame`，其余图片接到 `reference_1..9`。
- 其他分镜切换仍由各自的 `start_frame_prompt` 生成开始关键帧。

```text
├── run.log
```

`status.json` 状态：

## 固定限制

- 只接受 24 fps。
- `aspect_ratio` 必须包含 `9:16`。
- `final_width < final_height`，并保持竖屏比例。
- 参考图至少 1 张，最多 9 张。
- 每段时长必须大于 0。
- 每段提示词不能为空。
- 完整链未跑完时不会生成误导性的最终视频。


## 后处理与质检参数（2026-10 新增）

| 键 | 默认值 | 作用 |
|---|---|---|
| `two_pass_blend_frames` | `4` | 二采开头修复时，锚帧向正片渐变混合的帧数；`0` = 退回旧的硬切替换。混合可消除"定格后突然动起来"的跳变。 |
| `audio_boundary_fade` | `0.1` | 每个拼接边界的音频微淡入淡出时长（秒），消除脚步声/环境声硬接的爆音；`0` = 关闭。不改变时间线，A/V 永不失步。 |
| `qa_anchor_ssim_min` | `0.55` | QA 报告中，段首/尾解码帧对首尾锚帧 SSIM 的告警阈值，低于则标记 `first_frame_drift` / `last_frame_drift`。比较前会先把锚帧按视频宽高比中心裁切、双方高斯模糊并降到 96×96，消除分辨率/清晰度/宽高比差异带来的假告警（同段实测 0.60~0.97，跨段错配 <0.16）。 |
| `qa_face_check` | `false` | 是否启用人脸一致性检查（需安装 `insightface`，首次运行会下载 buffalo_l 模型）。 |
| `qa_face_sim_min` | `0.5` | 中间帧与参考图 1 人脸余弦相似度的告警阈值，低于则标记 `identity_drift`。 |
| `keyframe_reanchor_every` | `0` | 每 N 段对尾帧草稿提示词追加一次身份重锚定语句，抑制长链恒等漂移；`0` = 关闭。 |
| `keyframe_reanchor_prompt` | （内置语句） | 重锚定时追加到 `end_frame_prompt` 的提示词文本。 |

以上键均不参与 `generation_signature` 哈希（除重锚定文本本身已包含在其修改的提示词中），因此修改它们不会使既有段的生成缓存失效。

QA 结果写入每个 job 目录的 `qa_report.json`：每段含 `first_frame_ssim` / `last_frame_ssim`（可选 `identity_similarity`）与 `flags`；被标记的段可用 `--from-segment N --to-segment M` 单独重跑。

## 拼接行为

- 无视频淡出且首段尺寸等于 `final_width×final_height` 时，视频流以 `-c copy` 零损失直通，仅在需要音频微淡入时重编码音频轨；流复制失败会自动回退全量重编码。
- 存在故事切换点淡出或需要缩放时，回退到完整重编码路径（crf 18）。


关键帧链始终从第 1 段开始构建（命中缓存时零成本），只有区间内的段会真正渲染；全部段与当前配置一致时才自动合成成片。

## 扩图确认流程（2026-11-03 新增）

Director 节点新增控件 `confirm_reference_expand`（默认开）。开启时点执行的流程变为：

1. 只跑 `--stage preexpand`：把参考图1扩到成片比例（`work_dir/reference_expanded.png`），
   状态写入 job 的 `.state.json` → `reference_expand`（status/original/image/source/seed/attempts），
   同时把扩好的图顶到 `config.json` 的 `reference_images[0]`；
2. 面板弹「参考图已扩好，等你确认」卡（缩略图可点开原尺寸）：
   - **没问题，生成关键帧** → `POST /h3-long-video/reference/{id}/confirm`（标记 confirmed 并直接排队 keyframes）；
   - **重扩参考图** → `POST /reference/{id}/reroll`：从原始参考图重扩（seed = base_seed + 800000 + 第几次尝试，不会在扩图上叠扩）；
   - **换参考图** → `POST /reference/{id}/replace`：上传自己处理好的图，服务端等比放大 + 中心裁切到精确成片尺寸后顶替 `reference_expanded.png`（source=user）。
3. 确认后关键帧阶段 `preexpand_reference` 看到比例已对直接复用，全程零逐帧扩图。

不需要扩图时（比例差 ≤1%、`keyframe_reference_preexpand=false`、非 Qwen 后端、
`keyframe_align=off`）自动跳过，行为与旧版一致。CLI 手动跑同一 stage：

```bash
python run_h3_long_video.py --config <job>/config.json --stage preexpand [--force]
```

`--force` 从 `reference_expand.original` 记录的原图重扩。老任务（state 里没有
`reference_expand`）不受影响；单段节点不走预扩，无此控件。

## 云端出视频（RunningHub，2026-11-04 新增）

节点控件 `video_backend` 决定**视频阶段**跑在哪：

| 取值 | 行为 |
|---|---|
| `本地 ComfyUI（默认）` | 老链路：本机提交图，节点吐 `jobs/<id>`，产物在本地 output |
| `RunningHub 云端` | 首尾帧上传到 RunningHub → 提交平台上的 H3 fl2v 工作流 → 轮询 → 下载 mp4 回任务目录 `<job>/cloud/` |

**关键帧永远在本机出。** 云端没有 Qwen 关键帧链、也拿不到本地的参考图扩图，
所以「关键帧 → 确认 → 视频」这套流程不变：本机出帧、人工确认，进视频阶段才上云。

### 和本地链路的四个差异

1. **只有单采。** 段里的 `two_pass: true` 会被忽略（日志里有一行提示），
   云端工作流本身就是单采。想要二采就切回本地。
2. **渲染尺寸看 `runninghub.megapixels`。** 留空则用 `final_width×final_height`；
   填了 `0.3` 就是 `416×736`（按成片比例 × 像素预算，32 对齐）。
   成片尺寸不变——拼接阶段统一缩放到 `final_width×final_height`。
   *实测 0.3MP + 8 步：约 1.9 分钟/6 秒段，比本地 0.9MP 快一个量级。*
3. **末帧是抽出来的。** 本地链路节点直接吐末帧图，云端只回 mp4，
   runner 用 `ffmpeg -sseof -1 -update 1` 抽最后一帧存
   `<job>/cloud/segNN_last_<seed>_<taskId>.png`，下一段链式继承照旧。
4. **缓存签名含后端。** 切 `local` ↔ `cloud` 会重渲该段（签名里带了
   `video_backend` 和 `runninghub` 块），不会拿本地旧片冒充云端结果。

### config.json 的 `runninghub` 块

```json
"video_backend": "local",
"runninghub": {
  "host": "www.runninghub.ai",
  "api_key": "",
  "workflow_id": "2117808288889286657",
  "instance_type": "plus",
  "steps": 8,
  "fps": 24,
  "megapixels": 0.3,
  "retries": 2,
  "poll_interval": 5,
  "timeout": 3600,
  "node_map": {
    "first": ["114", "image"],
    "last": ["125", "image"],
    "prompt": ["139", "prompt"],
    "seed": ["133", "noise_seed", "int"],
    "steps": ["128", "steps", "int"],
    "width": ["139", "width", "int"],
    "height": ["139", "height", "int"],
    "frames": ["139", "length", "int"]
  }
}
```

| 字段 | 作用 |
|---|---|
| `api_key` / `workflow_id` | RunningHub 的 API Key 和平台上跑通的 H3 首尾帧工作流 ID。**仓库里 `api_key` 是空的**（repo 公开），真 key 放同目录的 `runninghub.local.json`（已 gitignore）：`{"api_key": "……"}`。也可以走环境变量 `RH_API_KEY` / `RH_WORKFLOW_ID` / `RH_HOST` |
| `steps` | 云端单采步数（默认 8）。H3 3 步 LoRA 也能跑，但 8 步明显稳 |
| `megapixels` | 云端渲染像素预算，见上文第 2 条；**只影响云端**，本地仍按 `megapixels` 走 |
| `frames` 映射 | 平台 conditioning 节点的 `length` 必须落在 `17n+5` 网格上，runner 按秒数**向上取**最近的合法值（5 秒 → 124 帧、6 秒 → 158 帧），和本地 `h3_frame_count` 同一套规则 |
| `node_map` | 用途 → `[节点 id, 字段名(, 类型)]`。照平台导出的 **API 格式**（不是 UI 格式）JSON 填；没映射的用途直接跳过 |

`node_map` 的键：`first` / `last` / `ref` 是图（值会被 upload 换成 fileName），
`prompt` / `seconds` / `seed` / `steps` / `width` / `height` / `megapixels` / `frames` 是值。
平台要求 `fieldValue` 类型跟原字段一致，数字字段要写第三项 `"int"`。

没有 `ref` 映射时，提示词里的 `<Picture 3> 定义…` 那句会被自动改写成
「以 `<Picture 1>` 首帧为身份基准」——云端只有首尾两张图，引用第三张会被
`strict_prompt_tags` 直接拒单（code 805）。

### 失败和重试

* 云端每次提交都真扣额度，所以 runner **不做自动重试**；`retries` 只是记在任务
  config 里备查。某段失败就单独 `--from-segment N --to-segment N --force` 重跑。
* 校验在 `validate_config` 里做：选了云端但缺 `api_key` / `workflow_id` / `node_map`
  会在**开跑前**报错，不会等关键帧全出完才失败。
* 断点续跑照旧：`.state.json` 里已有且签名一致的段跳过；云端段的 `prompt_id`
  形如 `cloud:<taskId>`，方便回溯是哪一次云端任务出的。
