# 工作台服务架构

> 本文给维护者看。写分镜 / 调参数不用读这份，去看
> [`segment编写规范.md`](./segment编写规范.md) 和 [`参数配置.md`](./参数配置.md)。

`tools/serve_app.py` 是唯一入口，一个 aiohttp 进程同时提供两个面板。
本文说明它怎么把两套路由挂到一起、每条路由归谁、以及改动时哪些地方会炸。

---

## 1. 进程结构

```
serve_app.py  (aiohttp, 默认 :8900)
│
├── SP.register_routes(routes, web)              ← 出片台，原生 aiohttp
│     └── selflift_panel.py  (26 条 /h3-long-video/*)
│
├── RB.register_remake_routes(routes, web, RP)   ← 复刻台，伪 handler 适配
│     └── remake_panel.py  (H.do_GET / H.do_POST，34 条 /api/*)
│
└── GET /health                                   ← 两个面板的挂载状态
```

**为什么独立于 ComfyUI**：

- ComfyUI 的 aiohttp 是模型服务的门面，重启 / 崩溃会让挂在它下面的页面一起 404。
- 网页每 3 秒轮询 status，如果 handler 里跑同步子进程，会冻住 ComfyUI 的 event loop。
- 独立后可以绑 `0.0.0.0` 给别的机器 / 手机用。

**零重复**：`serve_app.py` 里没有任何一条业务路由，它只做三件事 ——
import 两个模块、调各自的 `register_*_routes`、加 `/health`。

## 3. 伪 handler 的请求时序

复刻台一次请求的完整路径：

```
浏览器  GET /api/state?film=复刻_1117
   │
   ├─ aiohttp 匹配 GET /api/{tail:.*}          （注册在 FileResponse 之后）
   │
   ├─ _dispatch(request)
   │     ├─ raw = request.path_qs              （/remake/api/x 先剥前缀）
   │     ├─ body = await request.read()        （POST 才读）
   │     ├─ h = _FakeHandler(path=raw, headers=dict(request.headers), body=body)
   │     │       path     = str
   │     │       headers  = _Headers（大小写不敏感，对齐 email.message.get）
   │     │       rfile    = _FakeRFile（io.BytesIO，只实现 read(n)）
   │     │       wfile    = _FakeWFile（io.BytesIO，只实现 write/flush）
   │     │
   │     ├─ panel.H.do_GET(h)                  ← 关键：直接调类方法，不 new 实例
   │     │     H 内部照常 send_response(200) / send_header(...) / wfile.write(...)
   │     │     h._code 和 h._headers 被填，body 攒在 h.wfile.buf
   │     │
   │     └─ return web.Response(body=h.body, status=h.status, headers=...)
   │           （Content-Length 由 aiohttp 重算，transfer-encoding 丢弃）
   │
   └─ 浏览器收到
```

### 为什么不能 `H.__init__`

`H` 继承 `BaseHTTPRequestHandler`，构造时会去读 socket（`self.request`、
`self.connection`、`setup()`）。这里没有真 socket，所以 bridge 传自己的实例、
直接调 `H.do_GET(h)` —— Python 的实例方法只要求 `self` 有对应属性，
不要求是 `H` 的实例。

**代价**：`H` 里除了那 7 个成员，不能再引用别的实例状态。碰了
`self.server`、`self.client_address`、`self.request_version` 之类的属性，
合并模式下直接 `AttributeError`，而 `--standalone` 下又完全正常 ——
这类 bug 只在合并模式暴露，改完必须走 `serve_app.py` 验一遍。

## 4. 大文件为什么走 FileResponse

`/api/media` 的成片、`/api/src-video` 的源视频可能几十上百 MB。
伪 handler 是把响应体**攒齐在内存里**再发的，这类文件进去会直接吃满内存。

所以这两条路由单独实现：

```python
@routes.get("/api/src-video")
async def remake_src_video(request):
    ...
    return web.FileResponse(fp, headers={"Cache-Control": "no-store"})
```

`web.FileResponse` 自带 `Range` 支持（`206 Partial Content` + `Content-Range`），
前端时间轴 seek 依赖它。**注册顺序是硬约束** —— aiohttp 按注册顺序匹配，
`/api/{tail:.*}` 一旦先注册，`/api/media` 就永远进不来。

## 5. 端口与 build 号

`/api/version` 要报**真实**监听端口，但 `remake_panel.PORT` 是模块级常量，
而 `build_app()` 可能在 `argparse` 之前就被调用。所以 `serve_app.py` 用可变容器：

```python
_PORT = [8900]                      # main() 里 _PORT[0] = a.port
...
RP.PORT = _PORT[0]                  # build_app() 里读
```

三处 build 号必须同步改，否则前端「版本」提示会骗人：

| 文件 | 常量 |
|---|---|
| `selflift_panel.py` | `_PANEL_BUILD` |
| `remake_panel.py` | `UI_BUILD` |
| `web/selflift_app.html` | `const UI_BUILD` |

## 6. 资产：仓库副本 vs 活跃目录

这是全仓最容易误解的一处，**两个路径都存在、内容相同、但只有一个被读取**：

```
D:/Comfy-Desktop/.workbuddy/skills/h3-long-video/assets/     ← 运行时读这个（活跃）
D:/Comfy-Desktop/ComfyUI-Installs/h3-long-video-repo/skill/assets/   ← 入库副本（同步产物）
```

### 谁读哪个

| 常量 | 位置 | 指向 |
|---|---|---|
| `run_selflift.DEFAULT_WORKFLOW` | 活跃 scripts | 活跃 assets 的 `H3-SelfLift_单图参考.base.json` |
| `run_selflift.BLACKCRANE_BASE` | 活跃 scripts | 活跃 assets 的 `H3-SelfLift_黑鹤二采.base.json` |
| `run_selflift.GLOBAL_CFG_PATH` | 活跃 scripts | 活跃 assets 的 `selflift.global.json` |
| `remake_panel.BLACKCRANE_BASE` | **仓库根** | 活跃 assets（`SKILL_SCRIPTS` 的兄弟目录） |
| `selflift_schema.GLOBAL_CFG_PATH` | **仓库根** | 活跃 assets |

注意后两行：`remake_panel.py` 和 `selflift_schema.py` 本身住在仓库里，但它们
**显式拼出 `.workbuddy` 下的绝对路径**去读资产，不走仓库内的副本。这是刻意的 ——
两份面板代码在仓库里、配置在活跃目录，改配置不用动代码。

唯一有回退的是 `run_selflift.load_global_cfg()`：活跃目录缺失时才读本脚本旁的
`assets/selflift.global.json`。所以仓库副本的作用是「备份 + 让 clone 的人知道
该用什么工作流」，不是运行时依赖。

### 同步机制

`skill/scripts/sync_repo.py` 是活跃目录 → 仓库的单向同步器：

```bash
python skill/scripts/sync_repo.py --check   # 只读，列 DRIFT / MISSING / ORPHAN
python skill/scripts/sync_repo.py --apply   # 写过去，repo 侧统一 LF
```

同步范围（2026-11-17 起）：

- `scripts/*.py` 全部（**含 sync_repo.py 自身**）
- `SKILL.md`
- `assets/` 白名单：`*.base.json`、`selflift.global.json`、`remake_prompt.txt`、
  `segments.selflift.example*.json`、`storyboard.example.json`

`assets/` 用白名单而非整目录，因为那里混着 mp4、`*.prompts.html`、`*.state.json`、
`*.bak*`，都是本机产物。

### 提交时强制校验：`.githooks/pre-commit`

同步器是单向覆盖，靠人记着跑必然漏。仓库里 `.githooks/pre-commit` 会在提交前跑
`--check`，不同步就拦下：

```bash
git config core.hooksPath .githooks   # 每个 clone 启用一次
```

`core.hooksPath` 存在 `.git/config`，**不随仓库分发** —— clone 后必须手动启用，
否则 hook 形同不存在。hook 只检查不修复（写操作可能覆盖正在改的文件），拦下时
打印该跑的命令。活跃目录不存在时自动放行，方便别的机器 clone 后正常提交。

### 三种不同步状态

| 输出 | 含义 | 处理 |
|---|---|---|
| `[DRIFT]` | 两边内容不同 | `--apply` |
| `[MISSING]` | 仓库里没有 | `--apply` |
| `[ORPHAN]` | 仓库有、活跃目录没有 | 同步器不删，人工 `git rm` |

`ORPHAN` 是 2026-11-17 补的。此前只做单向覆盖，**「活跃目录删了、仓库还留着」
这种情况永远发现不了**，`--check` 照样报 ALL SYNCED —— 因为它只枚举活跃版有的文件。
`gen169.py` / `gen_neon_clean.py` / `gen_scenes_169.py` / `gen_walk_169.py` 四个
零引用脚本就是这么在仓库里躺了很久：活跃目录磁盘上压根没有，`master` 历史里也从未有过
（那几个脚本来自 `main` 早期 `959d640`，从没进过活跃目录）。

**历史教训**：加白名单之前，同步器只覆盖 `scripts/` 和 `SKILL.md`，两个 base
工作流和全局约束从来没进过仓库 —— 仓库里 `example_workflows/` 那堆示例看起来
像工作流，实际出片一份都不用，真正在跑的两份只活在本机。所以「同步通过」
不等于「资产齐了」，`--check` 的 `ALL SYNCED` 只证明它检查到的那些文件一致。

### 两个 git 仓库的关系

容易搞错的一点：活跃目录**不是本仓库的 checkout**，它是一个**独立的 git 仓库**
（2026-11-02 在该目录 `git init` 出来的，历史与 `main` 毫无关系）：

```
D:/Comfy-Desktop/ComfyUI-Installs/h3-long-video-repo/   分支 main   ← 全量工程，权威，唯一 remote
D:/Comfy-Desktop/.workbuddy/skills/h3-long-video/       分支 master ← 纯本地仓库，只有 skill/，无 remote
```

**历史沿革**：活跃目录早期自己挂过 `origin` 指向同一个 GitHub 仓库、推 `master`
分支。但 `main` 与 `master` **无 merge-base**（完全独立的历史），在活跃目录里
`git commit` 只会进 `master`，**永远进不了 `main`** —— 而且 `origin/master` 与
`main/skill/` 逐字节比对后 32 个文件零差异，纯属冗余镜像。2026-11-17 已
`git remote remove origin`：活跃目录降级为纯本地仓库（32 条 commit 全留），
从根上杜绝「push 成功 = 已同步」的错觉。

**所以「skill 同步到 main」只有一条路**：`sync_repo.py` 搬文件，不是 git 操作。
这正是 pre-commit hook 存在的理由。想给活跃目录留档，别 push，直接
`cp -r` 或 `git bundle` 到 `backups/`。

## 8. 已知的坑

| 症状 | 根因 |
|---|---|
| `/api/media?film=中文` 400 | Git Bash 下 curl 传中文 query 的编码问题，**不是服务故障**。用 Python `urlencode` 验 |
| 片名被截成第一个字 | 照抄 `H` 的 `q.get("film")[0]` 到 aiohttp 的 `MultiDict` 上。统一走 `parse_qs` |
| 时间轴拖不动 / 只能从头播 | `FileResponse` 注册在通配路由之后 |
| 伪 handler 里 `AttributeError` | `H` 引用了 7 个成员之外的状态 |
| 全片误标 `stale` | ComfyUI 重启刷了 `*_updated_at`，校正到最早一段 mp4 的 mtime 之前 |
| 提示词在日志里变方块 | 子进程没设 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1`，cp936 父进程解码 |
